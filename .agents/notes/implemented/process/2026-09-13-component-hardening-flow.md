# Agent Note: 加固链——既有组件"毛病很多"时的可复用流程

Status: implemented

## Problem

正向链（`grilling` → 规格 → 实施）解决"要做新东西"，反向链（`diagnosing-bugs` Phase 0 →
`dsh-incident-forensics`）解决"故障正在发生"，但第三类处境没有载体：**组件已存在、功能大致齐，
就是"各种问题"**——修一处碰一处、失败静默、文档对不上、不知道从哪下手（dsh-console 是当前实例：
`src/index.ts` 2178 行、单个 `ConsoleService` 扛 5 个职责 + 3 个角色、121 测试全绿仍挡不住）。

这类工作最容易滑向两种失败：**上来就重构**（没有台账与验收判据，没有终点、无法回滚），或
**按页面排批次**（页面是症状分布，不是依赖顺序，同一处代码被反复改）。两者都不是流程问题，
是**产出物形态**问题：缺一份"能分批执行、每批可验证可回滚"的方案。

## Decision

新增加固链，落为 skill [`.agents/skills/dsh-component-hardening/SKILL.md`](../../../skills/dsh-component-hardening/SKILL.md)，
六步各带退出闸门，**方案 = 批次表**（批次表被确认即视为方案定稿，实现只是执行）：

1. **目标可判定化**：把"做好"翻成 `操作 X → 现象 Y 消失`；每条必须写出验证方式，
   写不出的降级"待观察"、不进批次。
2. **只读取证**：命令产出的**事实台账** + **不一致清单**（文档说 A、实测 B）——文档只当线索。
3. **成因归类**：按六类归档（单点结构 / 权威源冲突 / 静默失败 / 边界未校验 / 状态不持久 / 陈旧文档），
   每条必须落到 `文件:行号`，停在"架构问题"等于没归因。
4. **分批排序**：安全 → 数据正确性 → 可观测性 → 体验；每批可独立合入、独立回滚，有依赖则串行。
5. **实施循环**：先写能红的复现（**无红即无修复**）→ 修 → 顺手把该块从大文件切出（切一次=一个提交）→ 全闸门。
6. **收口回灌**：文档同步到单点权威、不一致清单清空、复发面固化成命令、结论回灌 `grilling` 种子清单。

三条不变式贯穿：命令 > 记忆 > 文档 · 一个提交一个逻辑单元 · 能机械判定的才叫闸门。

## Alternatives

- **接进 `grilling` 当第四种模式**：拷问解决"边界没定"，加固解决"现状不清"——前者问人、后者问机器，
  混在一个 skill 里会让两种输入（用户决策 vs 实测输出）互相污染 → 否决，独立 skill。
- **接进 `diagnosing-bugs`**：反向链以"有故障现象"为前提，加固的起点往往是"说不上具体故障，就是不放心"
  → 前置条件不同，合并会让 Phase 0 的污染判定在无故障场景下空转。
- **只写成方法论文档（docs/ 或 note）**：读过即忘，与"机械闸门"主张自相矛盾 → 否决，落 skill
  （note 只记录决策与准入理由）。
- **引入 mattpocock 的 `request-refactor-plan` 承接**：它假设 issue tracker + 小步提交访谈，
  本仓库无 tracker（`.agents/skills/README.md` 已记该未装依赖），且它不覆盖"只读取证/成因归类/回灌"
  → 不采用，本 skill 自研。

## Consequences

- "毛病很多"不再以"大重构"开工：第一批动作是**只读命令取证**，产出的台账天然是后续每批的验收清单。
- 批次表成为可复用的方案形态——同一份表可以交给不同执行者（人或 agent），每批独立回滚。
- 与既有闸门衔接而非另造：第 5 步直接用 `pnpm typecheck` / `pnpm -r test` / `dsh-pre-push-checks`，
  第 6 步回灌 `grilling` 种子清单，三条链共用同一份高危面记忆（见
  [AICoding 方法论吸纳](2026-09-13-aicoding-methodology.md)）。
- 反模式清单来自既有事故：批里夹带顺手改（破坏回滚粒度）、把全绿测试当成没事（内部行为测试挡不住
  结构性问题，要的是先红后绿）、拿陈旧文档当事实（基线是伪的）。
