## A. Session persistence API：SessionHandle 取代旧方法集

**旧 API（rc.1）** — `dsh-v0.1.2-rc.1:packages/session/session-persistence/src/index.ts`：
`ctx.sessionPersistence` 服务方法：`locate / supportsRawArtifacts / readRaw / create(meta, inheritedEventCount?) / append(id, events) / load / inspect / borrowSession / readFrom / list / listSnapshots`。append 即承诺持久化；torn-tail 平衡在 load；写路径编排（PersistenceCoordinator / SessionPreparation / write-behind）由该包导出（`coordinator.ts`(1564 行)、`write-behind.ts`(159)、`preparations.ts`(401) 三个文件在 0.1.3 整文件删除）。

**新 API（0.1.3）** — `packages/session/session-persistence/src/index.ts` + `handle.ts`：
服务只剩 5 个抽象方法：`create(header) → SessionHandle(write)`、`open(id, access: 'read'|'write') → SessionHandle`、`flush()`、`stat(id)`、`list()`。
`SessionHandle`（`handle.ts`）：单 session 一条打开的通道，`read(offset,len) / append(events) / flush() / close()`，`access` 区分读写；append 为 best-effort，**flush 才是持久化屏障**；write handle = 该 session 唯一 mutator（"单写者所有权"）。错误集扩大：`SessionAlreadyOwnedError / SessionReadOnlyError / SessionHandleClosedError / SessionOwnershipLostError / SessionFormatUnsupportedError …`（`errors.ts`）。

**调用方迁移**：0.1.3 中 `sessionPersistence` 的消费者全部为官方内部包（agent-loop、agent、subagent/continuation、session-query 族、schedule、feedback、workspace、experimental/agent-team、acp 等，grep 结果）。**无任何 dsh-plugins 包引用 `sessionPersistence`**（`packages/*/src` grep 为空）。外部插件如果曾自己调旧方法（append/load/borrowSession…），需要改成拿 handle——我们没写这种代码。

**ctx.sessions（api-session-controller client）**：结构未变。
- `packages/api/session-controller/src/client/index.ts` rc.1 与 0.1.3 几乎逐行相同：`ctx.sessions: ISessions`、`inject`、remote 事件接线（`api-session/added|removed|…`）、`createScope/scopeOf` 全保留。
- `contract/sessions.ts`（ISessions 接口）**零 diff**。
- client 目录整体 10 文件 +422/−53：主要是**新增**（`assistant-stream.ts` 客户端、合约 events/snapshot 扩展）和 chat 提交面 `images → attachments` 改名（`PendingSubmissionImage → PendingSubmissionAttachment`，含 FileAttachmentRef）——只影响官方聊天 UI 的提交类型，不触我们插件。

## B. Session format v2 与旧数据

**版本号事实**：rc.1 `SESSION_FORMAT_VERSION = 0`（`dsh-v0.1.2-rc.1:packages/core/session/src/types.ts:87`）；0.1.3 `SESSION_FORMAT_VERSION = 2`（`packages/core/session/src/index.ts:86` 附近）。即 **rc.1 写的是代码口径 format v0**（release note 的"v1"是按产品口径数 0.1.2 代的说法；我们真实文件 header 就是 `version: 0`）。

**我们的真实文件证据**：`~/.dsh-web2/sessions/--home-long2015-Code-OpenCodeWiki--/session-98875ac2-…/session.jsonl.zstd` 解压后首行：
`{"type":"session","version":0,"id":"session-98875ac2-…","cwd":"/home/long2015/Code/OpenCodeWiki","delegationDepth":0,"agentPreset":"standard"}`，事件含 `permission/preset`、`sandbox/mode`、`approval/policy` 等 rc.1 词汇。rc.1 磁盘布局：`<sessions root>/<--cwd 清洗目录-->/session-<uuid>/session.jsonl(.zstd)`。

**v2 布局/schema**（0.1.3）：
- 文件命名（`packages/session/session-format/src/filename.ts`）：version 0 = `session.jsonl`；vN = `session.v{N}.jsonl`；+ 压缩后缀 `.zstd`。→ v2 文件 = `session.v2.jsonl.zstd`。
- 目录布局不变：`<root>/<project cwd 目录>/session-<id>/`，root 为必填配置（`session-persistence-jsonl` Config.root，无默认）。
- v2 头行新增必填 `isSeeded`，fork 继承切点从 header 数值改为末尾带 tag 的 `session/end-seed { inherited: true }` 事件；每行一个事件（v1/v0 的行打包/range 编码不同）；`sourceEventSeqs` 仍 range 编码；assistant 流从顶层 `assistant/chunk` 事件**嵌入** `assistant/message`（`session-format-v1-to-v2` README）。

**迁移是自动的、惰性的，无需手动命令**：
- `session-persistence-jsonl` 读路径：`findLog → resolveGenerationInDirectory`（选 session 目录里最高版本 generation）→ `requireStoredLog → ensureCurrentLog → ensureJsonlGenerationCurrent`（`generation.ts`）——把当前版本 generation 发布（写入 `session.v2.jsonl(.zstd)`）到同一 session 目录，**旧源文件作为不可变历史 generation 保留**（测试：generation.spec "publishes v1 beside an immutable suffixless v0 source"、"publishes only the final generation across a multi-edge migration"）。
- 迁移链：`session-format-catalog/src/generated.ts` `codecs: [releasedV0, releasedV1, releasedV2]`、`migrations: [v0→v1, v1→v2]`（v0→v1 包把 rc.1/旧 alpha 词汇归一化：steering/message→user/message 等；v1→v2 做 assistant-stream 嵌入与引用重映射）。
- 失败 fail-closed：未知/更新的格式 → `SessionFormatUnsupportedError`（"source artifact remains unchanged"，报错带原始文件路径，`index.ts ensureCurrentLog`）；**不会改写/删除旧文件**。
- 目录里同时存在 zstd 与非 zstd 编码 → 编码不匹配直接拒绝（不会猜）。

**对旧会话的结论**：升级到 0.1.3 后旧 v0 文件仍可被 list/stat 看到（released codec 可读旧 header），首次 open/resume 时自动出 v2 generation。数据不丢；但升级前仍建议对 `~/.dsh-web2/3/4`、`~/.dsh-daemon` 的 `sessions/` 做一次性备份，并在测试环境先验证一次真实旧会话的恢复。

## C. agentLoop.create 异步 + session 锁

- **签名**：rc.1 `create(id, options, meta): Agent`（同步，`dsh-v0.1.2-rc.1:packages/core/agent-loop/src/index.ts:652`）→ 0.1.3 `async create(...): Promise<Agent>`（`packages/core/agent-loop/src/index.ts:689`）。直接同步调用 `agentLoop.create(...).xxx` 的第三方代码会编译/运行破坏——官方自身调用方（agent-loop 内 startup/resume、agent、subagent 等）已随 0.1.3 改造。
- **写所有权/lock**：0.1.3 agent-loop 在 `setupAndPublish/resume` 处经 `persistence.create/open('write')` 先取 session 写所有权（注释 "Taking write ownership FIRST excludes a concurrent resume"）。跨进程锁由 `session-persistence-jsonl/src/lease.ts` 实现：POSIX 对 session 目录内 **`session.lock`** 文件 `flock(EX)`（Windows 为同名内核信号量），竞争映射为 `SessionAlreadyOwnedError`；进程崩溃由内核自动释放，无过期抢占；浏览器 worker 部署 stubs flock（单进程）。e2e：`lease.two-process.e2e.ts`。
- **对 host/子代理的间接影响**：packages/host 目录 src **零改动**（仅 7 个 package.json 版本号 bump）。子代理续跑（`subagent/subagent/src/continuation.ts`）等官方消费者改走 handle 所有权语义。**我们插件不调用 agentLoop / 不持有 session handle**，无直接波及。
- **多 dsh**：锁只约束"同一 DSH_HOME/sessions 下同一 session 目录"的并发写者。web2/3/4/daemon 各自独立 home ⇒ 无冲突；console 编排实例走远程 API（typert/gateway），不是共享 session 文件。唯一未来注意点：若某天让两个 harness 进程指向**同一个** sessions root，第二个写者会收到 `SessionAlreadyOwnedError`（比现在静默竞争写更安全）。

## 决策与后续（2026-09-05 用户拍板）

- **0.1.3-alpha.1 升级暂缓**：内核发布频率过高（rc.1 后隔日再出 alpha 新线），
  不逐版追。等 0.1.3 上 npm（当前仅 GitHub tag）+ 节奏稳定后再评估升级；
  届时本评估的"建议升级动作"清单直接可用（适配量小：备份 sessions/ →
  测试环境冷启验旧会话自动迁移 → 版本锁 + peer bump → typecheck/build →
  UI 冒烟）。
- **未来新开发对齐方向**：官方 0.1.3 的架构演进 = 我们后续写会话/生命周期
  相关新功能时的对齐参照——①session 写所有权收敛为单一 SessionHandle
  （append best-effort、flush 为持久化屏障）；②跨进程 session 锁（flock 于
  session.lock，同 sessions root 才有竞争）；③session format 版本链 + 惰性
  自动迁移（vN 文件与旧源并存，fail-closed）；④多 dsh（独立 DSH_HOME）天然
  避开锁竞争。新功能设计尽量落在这套语义上，避免自造偏离的持久化模型。
